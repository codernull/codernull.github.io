# Redis 缓存设计：热 key、区间扫描、修正失效与集群批量



## 0. 核心结论

Redis 缓存设计的第一件事不是选数据结构，是认访问模式。热点覆盖写 → STRING；区间取索引再取数据 → ZSET + HASH；整页查询 → STRING + 代次换键；TTL 是存活探针不是 GC；多 key 原子更新用 Lua，Cluster 上必须 hash tag；失效用 INCR 换键名而不是 UNLINK。业务只负责喂访问模式，Redis 只负责按原语兑现合同。

## 1. 访问模式 → 结构：四份原语合同

同一个业务域里，四种读流量长得很不一样，对应的 Redis 结构也完全不同。把它们列成表，每条都是一份"访问模式 → 原语"的合同：

| 访问模式 | 结构 | 合同内容 |
|---|---|---|
| 当前未闭合对象：高频覆盖写 + 需要自愈 | `STRING` + `EX 120` | 只保留最新一份；写者每次覆写续期，写者挂了 TTL 自然消失 |
| 近期已闭合区间：按时间范围取索引，再按索引取数据体 | `ZSET` + `HASH` 双键 | ZSET 管"有哪些、在哪个区间"，HASH 管"数据体在哪"，双键同步增删 |
| 深历史整页：一次查一个大区间，命中即整页返回 | `STRING` 整页缓存 | 拼装结果本身是原子单位，键名带版本号 |
| 修正代次：全局递增版本号 | `STRING` `INCR` | 单调递增天然适合"我比旧缓存新"的判定 |

为什么是这些结构，逐条说：

- **覆盖写用 STRING**：访问模式是"永远只看最新"，不需要历史、不需要排序。STRING 的 SET 天然覆盖，EX 附带过期，一次命令同时完成"写新值 + 续命"。
- **区间扫描用 ZSET + HASH**：只给一个结构会卡壳——只有 ZSET 没有 HASH，取数据要逐条 GET（N 次往返）；只有 HASH 没有 ZSET，无法按时间范围查。两个原语各管一半合同：ZSET 按 score（时间）给索引，HASH 按 field 给数据体。代价是双键必须同步，这条同步义务落到写路径（见第 3 节）。
- **整页查询用 STRING**：深历史页是"一次查完一个大区间、直接返回"的访问模式，拼装好的结果本身是原子单位，存 STRING 最自然。它的生命周期和 live/hist 都不同（TTL 1h 而不是永久），因为它是"可重算的中间结果"。
- **代次用 INCR**：修正后要"让所有旧页缓存失效"。INCR 一次递增，新键名带上新代次，天然形成"旧缓存不如新缓存"的偏序。

合同不只规定结构，还规定**写放大和失效策略**——见第 2、4、5 节。

## 2. TTL 是存活探针，不是 GC

`EX 120` 这个值第一次看容易误解成"120 秒没访问就删"。实际语义是**存活探针**：写者每次更新都覆写续期，TTL 的存在意义是"写者死了之后，缓存要自己消失"。

设计问题不是"多久没读就删"，而是"**读路径会不会读到僵尸数据**"。当前未闭合对象的写者是聚合服务，它每 tick 覆写一次。如果它挂了，live 键 120 秒后自然消失，读路径自动回落到"近期历史 + 回源"，不会对着一个永远不会再更新的"新鲜"值发呆。TTL 在这里承担的是故障自愈信号，不是缓存淘汰。

反面教材是拿 TTL 当 GC：假设某 key 业务上每 60 秒写一次，就把 TTL 也设成 60 秒——一旦上游抖动一次超过 60 秒，这个 key 就在两次写入之间蒸发，读路径回源。**TTL 应该按"写者的心跳周期 × 容忍的失联时长"设计，而不是按"读的频率"设计**。

## 3. 多 key 更新：Lua 原子 vs 分步，Cluster 要 hash tag

ZSET + HASH 双键是"两个 key 的合同"，双键必须同步增删，否则读路径会看到中间态：ZSET 里有一个 ws、HASH 里没有对应数据——用户图上就是一根点不开的柱子。所以封口这类"多 key 一起更新"的操作必须是原子的：

```text
桶封口（跨界时）：
  ZADD kl:hist:z:... ws ws
  HSET kl:hist:h:... ws <final bar>
  超长则 ZPOPMIN + HDEL 截断
  SET kl:live:... <新桶首帧> EX 120
```

分步执行必然有中间态，所以用 Lua 一把梭。这里有两个隐含条件：

- **单写者**：同一 key 只有聚合服务一个写者（分片 + 租约），Lua 里不需要考虑并发写冲突。单写者前提下，Lua 原子性绰绰有余。
- **Cluster 上必须 hash tag**：这是选 Lua 时被绑定的隐藏合同——Lua 脚本里所有 key 必须落在同一个 slot，否则 Cluster 直接报 CROSSSLOT。所以键名必须带 `{symbol}`：

```text
kl:hist:z:{symbol}:{window}    kl:hist:h:{symbol}:{window}
```

`{...}` 让 Redis 只对花括号内的部分算 slot，同一 symbol 的所有键必然同节点。**如果先选了 Lua、后补 hash tag，等于重命名一批线上键；应该在设计键名时就留好**。这也是"原语合同"的一部分：结构选型和集群约束是同时生效的。

## 4. 失效：INCR 换键名，不做删除风暴

修正场景（历史数据错了要改）里，一次修正会让"深历史整页缓存"整体作废。直观做法是遍历删除所有相关页键，但这条路在 Redis 上是反模式：

- 一次修正可能命中几十上百页，UNLINK 风暴本身就会打满主线程（和单线程文呼应：删除也是命令执行）；
- 删除是 O(页数) 的，且要遍历拿到全部键名。

方案是**换键名**：页键名里带代次号 `kl:page:{symbol}:{window}:{epoch}:{page}`，修正时 `INCR kl:epoch`——新查询自然落到新代次的键上，旧键等 TTL 回收：

```text
历史修正:
  HSET 覆写受影响 ws 的 value        # 历史数据本身
  INCR kl:epoch                       # 所有旧页键整体作废（O(1)）
```

失效成本从 O(页数) 降到 O(1)，而且没有删除命令、没有删除风暴。**"整体失效一批缓存"的通用做法是版本号进键名，而不是遍历删除**——删除是给"单点数据过期"用的，代次是给"批量数据作废"用的，两者不是一回事。

## 5. 写放大：live 每 tick 写、hist 只在封口写

两类的写频率差两个数量级：live 每次行情更新都写（tick 级），hist 只在窗口封口写（分钟/小时级）。这个差异直接决定热路径的形状：

- 每 tick 路径要尽量短：一个 `SET ... EX 120`，没有 Lua、没有多个 key——因为 tick 级写放大直接打在 Redis 的命令执行上；
- 重的原子操作（Lua 封口）全部挪到低频路径（封口时），高频路径只保留轻原语。

这里和《Redis 还是单线程》只点一句，不做续集：**Redis 命令执行单线程，所以"每 tick 写"必须是一个轻原语，任何把计算塞进 tick 路径的设计（比如把聚合逻辑写进 Lua）都会在突发下顶住主线程**。本文的键设计就是这条约束的产物：计算留在聚合服务内存里，Redis 只收结果。

## 6. 集群批量：按节点分组，失败只许"没分组"

第二个 Redis 场景是客户端路由，不是业务故事。上了 Redis Cluster 之后，批量操作撞上硬边界：**pipeline 只能发给一个节点，一批 key 分布在多个节点上，就得先按节点分组，再逐节点执行**。某个共享缓存组件里有个小工具就是干这个的（脱敏复述核心逻辑）：

```java
// 预构建 slot → 节点索引 映射表（一次 O(M×S)，S 是单节点 slot 数）
List<RedisClusterNode> partitions = clusterConn.getPartitions().getPartitions();
Map<Integer, Integer> slotToNodeIndex = new HashMap<>(16384);
List<List<String>> keyGroups = new ArrayList<>(partitions.size());
for (int i = 0; i < partitions.size(); i++) {
    keyGroups.add(new ArrayList<>());
    for (int slot : partitions.get(i).getSlots()) {
        slotToNodeIndex.put(slot, i);
    }
}

// 每个 key 直接查表，O(N)，不循环匹配所有节点
for (String key : keys) {
    int slot = SlotHash.getSlot(key);          // 用客户端库的 CRC16，保证和路由一致
    Integer nodeIndex = slotToNodeIndex.get(slot);
    if (nodeIndex != null) {
        keyGroups.get(nodeIndex).add(key);
    } else {
        notFoundNodes.add(key);                // slot 未映射（节点下线等极端情况）
    }
}
```

三个设计点：

- **映射表而不是循环匹配**：直观写法是"每个 key 算 slot → 遍历节点找包含它的"（O(N×M)）。预构建 slot→节点索引表后查表 O(1)，整体 O(N)。一批几万 key 的巡检，这差别是几十毫秒和几百毫秒。
- **用客户端的 `SlotHash` 而不是自己实现 CRC16**：分组结果必须和客户端实际路由逐 bit 一致，否则分错组。直接用 Lettuce 的哈希实现，不做第二个实现。
- **失败只许"没分组"**：工具出错的最坏后果是没分组（性能劣化，多跑几轮），不能是分错组（把 key 发给错误节点，那是事故）。所以异常降级为单机模式（全量一组），未映射 slot 单独收集告警，不混进正常组。

这个工具本身很简单，价值在于把"集群批量必须按节点分组"这条合同变成可复用组件——任何批量删 key、按节点巡检、容量分析都建立在它上面。

## 7. 领域负荷（半页）：这些场景为什么存在

上文所有合同背后只有一个业务属性撑腰：**Redis 不是源，是可重建的**。K 线系统只把 1m K 线落 ClickHouse，9 个派生窗口全部内存现算，Redis 里的一切都能从 ClickHouse 重算回来——所以它敢用 TTL 心跳（挂了就消失，回源重建）、敢用 epoch 换键名（旧页等回收，不删）、敢整体重建（重启后重算 9 个窗口回填）。

反过来说，如果 Redis 是源，上面每个决策都要改：TTL 心跳会丢数据、换键名会丢页、重建无从谈起。**"可重建性"放开了 Redis 的胆子，业务只需要喂访问模式**——本文没有讨论窗口对齐、夏令时、推送帧协议，那些是业务自己的合同，和 Redis 无关。

## 8. 复盘

如果再设计一次这套缓存，顺序会倒过来：**先列访问模式清单，再选原语，最后才让业务对号入座**。现在文章里"访问模式 → 结构"的映射表看着顺理成章，实际当时是业务先跑起来、Redis 后补的，代价是键名补 hash tag、失效从删除改成换键这两次返工。

五个决策没有一个是 K 线专属的：心跳 TTL、ZSET+HASH 区间、epoch 换键失效、Lua + hash tag 原子更新、按节点分组批量——换任何"热 key + 区间扫描 + 修正失效 + 集群批量"的业务场景都成立。这也是把它们从业务故事里拆出来写成 Redis 设计文的原因。
