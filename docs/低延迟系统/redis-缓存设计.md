# Redis 缓存设计：热 key、区间扫描、修正失效与集群批量

> 素材来自两份内部材料（已脱敏）：一份 K 线聚合推送实施方案，一份共享缓存组件 `RedisKeyGroupServiceImpl`。K 线只是产生 Redis 场景的载体，本文主语是 Redis：访问模式怎么映射到原语、多 key 更新怎么保证原子、失效怎么做才不打删除风暴、集群批量怎么按节点分组。

## 1. 背景与动机

做推送系统的缓存层时，团队里经常能听到几种说法：

- "热数据放 Redis，QPS 就能扛住。"
- "区间数据？ZSET 就行。"
- "缓存失效？删掉重写。"
- "Cluster 批量操作直接 pipeline。"

这些说法单独看都没错，合在一起就漏了关键一层：**Redis 原语之间有明确的分工和约束，结构选型必须跟着访问模式走，而不是跟着"哪个结构好听"走**。选错结构的代价不会立刻暴露，只会在某个流量拐点变成"为什么 Redis 顶着 80% CPU 还慢"的线上问题。

这篇文章把缓存设计拆成四份"访问模式 → 原语"合同，加上两个横切约束（多 key 原子、集群路由），记录我在两套内部素材里验证过的设计。K 线只是产生这些场景的载体，真正的主题是 Redis。

## 2. 访问模式 → 结构：四份原语合同

先交代一次访问的完整路径，不然下面的结构选择没有上下文。这个业务里读路径有三种流量：

1. **当前未闭合对象**：每 tick 更新，读方只要最新一份；
2. **近期已闭合区间**：按时间范围拉一段，先要"有哪些、在哪个区间"，再要"数据体"；
3. **深历史整页**：一次查一个大区间，命中直接整页返回。

三种流量对应三种访问模式，加上一种特殊的写模式"批量作废"，共四份合同：

| 访问模式 | 结构 | 合同内容 |
|---|---|---|
| 当前未闭合对象：高频覆盖写 + 需要自愈 | `STRING` + `EX 120` | 只保留最新一份；写者每次覆写续期，写者挂了 TTL 自然消失 |
| 近期已闭合区间：按时间取索引 → 按索引取数据 | `ZSET` + `HASH` 双键 | ZSET 管"有哪些、在哪个区间"，HASH 管"数据体在哪"，双键同步增删 |
| 深历史整页：一次查大区间，命中整页返回 | `STRING` 整页缓存 | 拼装结果本身是原子单位，键名带版本号 |
| 批量作废：一次修正 → 一批页全废 | `INCR` 代次 | 单调递增，天然形成"代次大的更新"的偏序 |

下面逐个推演为什么是这些结构——不是"ZSET 适合区间"，而是"这个访问模式逼出了这个结构"。

### 2.1 覆盖写为什么是 STRING

当前未闭合对象的访问模式是"永远只看最新"。这个模式有两个特征：读方不需要历史、不需要排序；写方每次来都是整份覆盖。

两个特征直接排除 ZSET 和 HASH：

- **ZSET** 的存在理由是排序，代价是每个 member 要在 skiplist 上 O(log n) 定位。这里没有排序需求，排序能力用不上，开销白付；
- **HASH** 的存在理由是"一个键下多个 field 独立读"。这里只有一个值，field 维度用不上，还多一层结构头。

`STRING` 的 `SET` 天然覆盖，加上 `EX` 参数一次命令同时完成"写新值 + 续命"。这个"续命"很关键——它不只是 TTL，它是写者还活着的证明，第 3 节专门讲。

### 2.2 区间扫描为什么是 ZSET + HASH

近期已闭合区间要回答两个问题：这个时间范围里有哪些窗口？每个窗口的数据体是什么？

只给一个结构都卡壳：

- **只有 ZSET**：member 是窗口 id、score 是时间。`ZRANGEBYSCORE` 能拿到 id 列表，但数据体在哪儿？逐条 GET 是 N 次往返；把数据体塞进 member 就要整个序列化，查任何区间都得把整对象取出来再过滤，序列化成本白付。
- **只有 HASH**：数据体按 field 存没问题，但 HASH 没有按时间排序的能力，回答不了"这个范围里有哪些"。

两个结构各管一半合同：ZSET 按 score 给索引，HASH 按 field 给数据体。查询路径是两条命令，先拿索引、再批量取数据：

```text
ZRANGEBYSCORE kl:hist:z:{symbol}:{window} startTs endTs   # 窗口 id 列表
HMGET kl:hist:h:{symbol}:{window} <id1> <id2> ...         # 批量取数据体
```

ZSET 管序、HASH 管值，代价是**双键必须同步增删**——这条同步义务落到写路径上，正是第 4 节 Lua 的由来。结构选型和写路径约束是一起定下来的，不是分开的两件事。

### 2.3 整页为什么是 STRING

深历史页的访问模式是"一次查完一个大区间、直接返回"。如果只依赖 ZSET+HASH，一次深历史请求要拼 N 个窗口的数据体再组装，等于把"组装"这件事放在每次请求里重做。

`STRING` 整页缓存把"区间查询 + 组装"的结果整体缓存下来：拼装结果本身是原子单位，读路径一次 `GET` 命中即返回。代价是失效粒度变粗——一页里任何一个窗口变了，整页都过期。这个粗粒度失效正是第 5 节"换键名而不是删除"的出发点，两条设计是配套的：**整页缓存只有搭配代次失效才成立**，单独用会退化回"删了重写"。

### 2.4 代次为什么是 INCR

批量作废需要一个"版本号"，让新查询天然落到新版本上。这里不能用 `SET` 覆盖（多读者并发读旧值再写有竞态），要的是单调递增的计数器——`INCR` 一次命令完成，天然形成偏序。第 5 节讲它怎么用，这里先记住结论：**代次是一个 O(1) 的全局失效开关**。

## 3. TTL 是存活探针，不是 GC

`EX 120` 这个值第一次看容易误解成"120 秒没访问就删"。它的真实语义是**存活探针**：写者每次更新都覆写续期，TTL 的存在意义是"写者死了之后，缓存要自己消失"。

设计问题不是"多久没读就删"，而是"**读路径会不会读到僵尸数据**"。把写者挂掉的完整时序推演一遍：

```text
t0      聚合服务最后一次覆写 live 键（TTL 重置为 120s）
t0+120s TTL 到期。Redis 惰性删除：读路径下次访问这个键时发现已过期，返回空
t0+120s+读路径自动回落：近期历史 + 回源重建
```

关键在 t0+120s：读路径不会对着一个永远不会再更新的"新鲜"值发呆，而是自动 miss、自动回源。TTL 在这里承担的是**故障自愈信号**，不是缓存淘汰。

那为什么是 120 而不是 30 或 300？看两个方向上的代价：

- **太短**：聚合服务重启 + 回源重建的时间超过 TTL，恢复期间读路径持续 miss、持续回源，把峰值压力打给持久层；
- **太长**：僵尸数据存活太久，写者真的死了，读方还要对着旧数据看几分钟。

120 是"重启 + 重建够用"和"僵尸数据不过夜"之间的折中——**按写者的心跳周期 × 容忍的失联时长设计，而不是按"读的频率"设计**。

反面教材是拿 TTL 当 GC：假设某个 key 业务上每 60 秒写一次，就把 TTL 也设成 60 秒——上游一次抖动超过 60 秒，这个 key 在两次写入之间蒸发，读路径回源，一次瞬时抖动被放大成雪崩。TTL 的过期语义是"时间到就删"，不是"没人用就回收"，用错方向会把抖动放大成故障。

## 4. 多 key 更新：Lua 原子 vs 分步，Cluster 要 hash tag

ZSET + HASH 双键的合同是"双键同步增删"，但同步这件事 Redis 不帮你做。封口（窗口闭合）要同时动四类东西：ZSET 加新 member、HASH 写数据体、超长时截断最老、live 键换新桶。分步执行的中间态很具体：

```text
步骤 1 完成、步骤 2 未执行：
  ZSET 里已经有一个新窗口 id
  HASH 里还没有对应 field
  读路径 ZRANGEBYSCORE 拿到这个 id → HMGET 拿到空 → 返回一根"点不开"的柱子
```

这个中间态窗口虽然短，但读路径是高频轮询，必然会撞上。所以封口必须原子——用 Lua 一把梭：

```text
桶封口（跨界时）：
  EVAL "
    ZADD kl:hist:z:{symbol}:{window} score id
    HSET kl:hist:h:{symbol}:{window} id <final bar>
    长度超限则 ZREMRANGEBYRANK 截断最老 + HDEL
    SET kl:live:... <新桶首帧> EX 120
  "
```

选 Lua 的同时被绑定了两个前提：

- **单写者**：同一 symbol 只有聚合服务一个写者（分片 + 租约保证）。单写者前提下，Lua 原子性绰绰有余；如果将来放开多写者，Lua 保证的还是"一组命令不被打断"，业务层要另补幂等。
- **Cluster 上必须 hash tag**：Lua 脚本里所有 key 必须落在同一个 slot，否则直接报 CROSSSLOT。Redis 的 hash tag 规则是只对 `{` 与 `}` 之间的内容计算 CRC16，所以键名要设计成：

```text
kl:hist:z:{symbol}:{window}    kl:hist:h:{symbol}:{window}
```

`{symbol}` 让同一个 symbol 的所有键必然同 slot。为什么用 symbol 做 tag 而不是 window？因为原子更新的对象是"一个 symbol 的一批键"，tag 必须落在"一起事务更新的最小单位"上——这是 hash tag 选择的唯一正确标准。

这条约束的教训是：**如果先选 Lua、后补 hash tag，等于重命名一批线上键**；应该在设计键名时就留好。结构选型和集群约束是同时生效的，不是两件事。

## 5. 失效：INCR 换键名，不做删除风暴

修正场景（历史数据错了要改）里，一次修正会让"深历史整页缓存"整体作废。直观做法是遍历删除相关页键，但这条路在 Redis 上是反模式。把删除方案的代价算一遍：

```text
一次修正命中几十上百页：
  方案 A（遍历删除）：
    先拿键名——KEYS 会在主线程阻塞；SCAN 要多次往返，每次拿一批
    再逐条 UNLINK——UNLINK 本身 O(1) 异步回收，但几十上百条命令在主线程上串行调度
  方案 B（换键名）：
    INCR 一条命令，全部作废
```

`UNLINK` 不是罪魁祸首——异步回收让大 value 删除不再阻塞主线程。真正的成本是：拿键名的往返、几十上百条命令在主线程上的串行调度、以及"修正"这个低频操作反而占了高频路径的注意力。方案 B 是：

```text
历史修正:
  HSET 覆写受影响窗口的 value        # 历史数据本身
  INCR kl:epoch                       # 所有旧页键整体作废，O(1)
```

键名带代次：`kl:page:{symbol}:{window}:{epoch}:{page}`。新查询自然落到新代次的键上，旧键等 TTL 回收（整页键 TTL 1h，最坏一小时内内存里有两代页，可接受）。

这里有一条通用原则：**删除是给"单点数据过期"用的，代次是给"批量数据作废"用的**。判断标准是失效的粒度——单点过期用 TTL/DEL，批量作废用版本号进键名。混用的典型事故就是把批量作废做成了循环删除，遇到一次修正几百页的场景就变成删除风暴。

## 6. 写放大：live 每 tick 写、hist 只在封口写

两类键的写频率差两三个数量级：live 每次行情更新都写（tick 级），hist 只在窗口封口写（分钟/小时级）。这个差异直接决定热路径的形状：

- **每 tick 路径要尽量短**：一次 `SET ... EX 120`，没有 Lua、没有多个 key。理由和上篇《Redis 还是单线程》只点一句：命令执行在主线程，tick 级写放大直接打在命令执行上，把任何计算塞进 tick 路径（比如把聚合逻辑写进 Lua），突发时主线程被占满，所有客户端排队，p99 起飞。本文的键设计就是这条约束的产物：计算留在聚合服务内存里，Redis 只收结果。
- **重的原子操作（Lua 封口）全部挪到低频路径**（封口时）。这还有一层收益：`ZADD` 在 skiplist 上是 O(log n) 插入，如果它出现在每 tick 路径上，就是每 tick 一次 O(log n)；低频封口让这个维护成本被摊到分钟级，而不是 tick 级。

## 7. 集群批量：按节点分组，失败只许"没分组"

第二个 Redis 场景是客户端路由，不是业务故事。Redis Cluster 用 16384 个 slot 分片，`key → slot = CRC16(key) % 16384`，客户端按 slot 路由，跨节点会收到 MOVED 重定向。所以"批量操作"在 Cluster 上有个硬边界：**pipeline 只能发给一个节点，一批 key 分布在多个节点上，就得先按节点分组，再逐节点执行**。

共享缓存组件里有个小工具就是干这个的（脱敏复述核心逻辑）：

```java
// 预构建 slot → 节点索引 映射表（一次 O(M×S)，S 是单节点 slot 数）
List<RedisClusterNode> partitions = clusterConn.getPartitions().getPartitions();
Map<Integer, Integer> slotToNodeIndex = new HashMap<>(16384);
List<List<String>> keyGroups = new ArrayList<>(partitions.size());
for (int i = 0; i < partitions.size(); i++) {
    keyGroups.add(new ArrayList<>());
    for (int slot : partitions.get(i).getSlots()) {
        slotToNodeIndex.put(slot, i);
    }
}

// 每个 key 直接查表，O(N)，不循环匹配所有节点
for (String key : keys) {
    int slot = SlotHash.getSlot(key);          // 用客户端库的 CRC16，保证和路由一致
    Integer nodeIndex = slotToNodeIndex.get(slot);
    if (nodeIndex != null) {
        keyGroups.get(nodeIndex).add(key);
    } else {
        notFoundNodes.add(key);                // slot 未映射（节点下线等极端情况）
    }
}
```

三个设计点值得单独说：

- **映射表而不是循环匹配**：直观写法是"每个 key 算 slot → 遍历节点找包含它的"（O(N×M)）。预构建 slot→节点索引表后查表 O(1)，整体 O(N)。一批几万 key 的巡检，差别是几十毫秒和几百毫秒。
- **用客户端的 `SlotHash` 而不是自己实现 CRC16**：分组结果必须和客户端实际路由逐 bit 一致，否则分错组。直接用 Lettuce 的哈希实现，不做第二个实现——这是"正确性不重复造轮子"的典型。
- **失败只许"没分组"**：工具出错的最坏后果是没分组（性能劣化，多跑几轮），不能是分错组（把 key 发给错误节点，那是事故）。所以异常降级为单机模式（全量一组），未映射 slot 单独收集告警，不混进正常组。

"失败只许没分组"是这条设计的验收标准。写这类工具时先想清楚"出错的最坏后果是什么"——**能退化，不能越界**。

## 8. 领域负荷（半页）：这些场景为什么存在

上文所有合同背后只有一个业务属性撑腰：**Redis 不是源，是可重建的**。K 线系统只把 1m K 线落持久层，9 个派生窗口全部内存现算，Redis 里的一切都能重算回来——所以它敢用 TTL 心跳（挂了就消失，回源重建）、敢用 epoch 换键名（旧页等回收，不删）、敢整体重建（重启后重算 9 个窗口回填）。

反过来说，如果 Redis 是源，上面每个决策都要改：TTL 心跳会丢数据、换键名会丢页、重建无从谈起。**可重建性放开了 Redis 的胆子，业务只需要喂访问模式**。本文没有讨论窗口对齐、夏令时、推送帧协议，那些是业务自己的合同，和 Redis 无关。

## 9. 复盘与后续

如果再设计一次这套缓存，顺序会倒过来：**先列访问模式清单，再选原语，最后才让业务对号入座**。实际当时是业务先跑起来、Redis 后补的，代价是键名补 hash tag、失效从删除改成换键两次返工。

五个决策没有一个是 K 线专属的，换任何"热 key + 区间扫描 + 修正失效 + 集群批量"的业务场景都成立：

1. 覆盖写 + 自愈 → `STRING` + TTL 心跳；
2. 区间索引 + 数据 → `ZSET` + `HASH`，双键同步义务落到写路径；
3. 整页命中 → `STRING` + 键名带代次；
4. 多 key 原子更新 → Lua，Cluster 上 hash tag；
5. 批量作废 → INCR 换键名，不遍历删除。

后续如果再动这套系统，我会先补两件事：把"访问模式清单"做成每个新需求的必填项（先答访问模式，再谈结构）；给集群批量工具补一组故障注入测试（节点下线时未映射 slot 的收集路径，验证"只许没分组"）。

| 语义 | 出处 | 结论 |

| `UNLINK` | redis.io UNLINK | 异步回收内存，不阻塞主线程 |
| `ZADD` 复杂度 | redis.io ZADD | 每 member O(log n)，skiplist |
