# 撮合引擎核心：订单簿结构、撮合语义与并发读取

> 素材来自本仓库 `matching-engine`（Go 实现，MIT License）。文中“撮合引擎”指价格/时间优先订单簿的完整实现：新增、撮合、撤单三类操作与并发读取，不含行情接入、风控与清算。所有源码片段标注文件与函数，可在本仓库直接复现。

## 0. 核心结论

撮合引擎的正确性九成在数据结构选型与撮合语义边界：价格/时间优先用 Skiplist + 每档 FIFO + 订单索引；成交价取被动方价格；买卖盘档位必须分离存储，共用档位表会破坏时间优先。档位查找 O(log n)，撤单 O(1)。

## 1. 背景与约束

撮合引擎是交易链路里最不该出错的一段逻辑：一笔订单进来，要么吃掉对面盘口的单子当场成交，要么挂进盘口等别人来吃，要么被撤掉。成交记录直接决定资金和持仓的归属，所以**语义正确比快更重要**——下面所有结构选型和代码组织，都是被这一条逼出来的。

它要满足的约束只有四条，但每一条都对应一个独立的正确性陷阱：

| 约束 | 含义 | 直接后果 |
|---|---|---|
| 价格优先 | 买盘高价优先，卖盘低价优先 | 需要“按价格取最值”的数据结构 |
| 时间优先 | 同一价格档位内先到先成交 | 每档必须是有序队列，且买卖盘各自独立 |
| 部分成交 | 撮合数量 = min(双方剩余量) | 未成交完的订单要留在队首继续参与下一轮 |
| 撤单 | 未成交的订单可以按订单号撤销 | 需要 O(1) 定位订单在盘口中的位置 |

## 2. 系统架构

代码拆成三个包，职责硬切开：`book` 是纯状态，回答“盘口现在长什么样”；`engine` 做唯一的语义决策，回答“该不该成交、以什么价成交”；`feed` 回答“事件从哪来”。

```text
matching-engine/
├── cmd/orderbook/      # CLI：读文件 → 喂给引擎 → 打印成交与盘口
├── internal/
│   ├── order/          # 数据模型：Order / Event / Trade
│   ├── book/           # 订单簿：纯状态，不做任何业务决策
│   ├── engine/         # 撮合引擎：消费事件、维护盘口、产出成交
│   └── feed/           # 行情文件并发读取：IO 与撮合解耦
└── testdata/sample.txt # 示例输入
```

分层不是为代码整洁，是为了**让决策层不碰 IO**：撮合逻辑只依赖内存里的订单簿状态，任何磁盘读、网络收包都不该混进撮合路径。这是低延迟系统里通用的分法——IO 是一层，状态是一层，决策是一层。好处在调试时体现得最明显：撮合结果错了只盯 `engine`，盘口状态乱了只盯 `book`。

## 3. 订单簿数据结构

### 3.1 语义到结构的映射

四条约束翻译成数据结构，是三个独立部件协作：

| 语义 | 数据结构 | 为什么 |
|---|---|---|
| 价格优先（按价格取最值） | Skiplist，key = 价格 | 有序集合，买盘取 Max、卖盘取 Min 都是 O(1) |
| 时间优先（同价先到先成交） | `container/list`，每档一个 FIFO | 队首即最早订单，部分成交后留在队首 |
| 撤单（按订单号定位） | `map[string]*slot` | slot 记录方向、价格、链表节点，O(1) 摘除 |
| 档位 ↔ 队列关联 | `map[int64]*level` | 价格 → 该档 FIFO；档位删空时同步删 Skiplist key |

### 3.2 Skiplist：为什么是它

候选方案有三个：map 套排序、红黑树、跳表。

- **map + 排序**先被排除：撮合每成交一笔都要取一次最优价，全量排序 O(n log n)，量级上来就完蛋。
- **红黑树（std::map）**能用，但实现像黑盒，而且想给盘口加并发时，跳表的层指针天然支持锁分段，红黑树改起来痛苦得多——LevelDB、Redis 的 zset 都是跳表，就是这个原因。
- **Skiplist**：插入/删除 O(log n)，取最值 O(1)——第 0 层链表的头尾节点直接就是最小/最大值；实现一百来行，坏了能一眼看懂。

选跳表就一句话：**够用、能看懂、以后想并发改造有路走**。订单簿的档位集合是稀疏的（价格分布广，档位数远小于订单数），跳表在这种稀疏 key 上比连续数组合适。

`Insert` 和 `Delete` 是这棵跳表的全部核心（`skiplist.go`）：

```go
// Insert 插入 key，返回是否为新 key（已存在则返回 false，不重复插入）。
func (s *Skiplist) Insert(key int64) bool {
	update := make([]*node, maxLevel)
	cur := s.head
	for i := s.level - 1; i >= 0; i-- {
		for cur.next[i] != nil && cur.next[i].key < key {
			cur = cur.next[i]
		}
		update[i] = cur
	}
	if nxt := cur.next[0]; nxt != nil && nxt.key == key {
		return false
	}
	lv := s.randomLevel()
	if lv > s.level {
		for i := s.level; i < lv; i++ {
			update[i] = s.head
		}
		s.level = lv
	}
	nd := &node{key: key, next: make([]*node, lv)}
	for i := 0; i < lv; i++ {
		nd.next[i] = update[i].next[i]
		update[i].next[i] = nd
	}
	return true
}

// Delete 删除 key，返回是否存在。
func (s *Skiplist) Delete(key int64) bool {
	update := make([]*node, maxLevel)
	cur := s.head
	for i := s.level - 1; i >= 0; i-- {
		for cur.next[i] != nil && cur.next[i].key < key {
			cur = cur.next[i]
		}
		update[i] = cur
	}
	tgt := cur.next[0]
	if tgt == nil || tgt.key != key {
		return false
	}
	for i := 0; i < s.level; i++ {
		if update[i].next[i] != tgt {
			break
		}
		update[i].next[i] = tgt.next[i]
	}
	for s.level > 1 && s.head.next[s.level-1] == nil {
		s.level--
	}
	return true
}
```

层数由 `randomLevel` 按 1/2 概率逐层上升；`Min`/`Max` 分别是第 0 层头节点和从最高层向右走到头。两段代码里最关键的是 `Insert` 的返回值：`false` 表示价格档位已存在。订单簿只在首次出现某价格时建档，重复插入必须被忽略——否则档位删空时会留下幽灵节点。

### 3.3 买卖盘必须分开：测试先红的一次

这个实现里唯一一次“测试先红”，是买卖盘共用档位表的版本。同价格的买单和卖单挤进同一个队列，撮合循环从队首取买单、从队尾取卖单，时间优先在同一档上被破坏，甚至可能撮合到同一笔单子自己吃自己。

修复是把档位彻底拆开：`bidLvls`/`askLvls` 两张表、`bids`/`asks` 两棵跳表。买盘和卖盘从此是两个独立的序，互不干扰。

```go
type OrderBook struct {
	bids    *Skiplist // 买盘价格档位集合（升序存储，最优买价取 Max）
	asks    *Skiplist // 卖盘价格档位集合（升序存储，最优卖价取 Min）
	bidLvls map[int64]*level
	askLvls map[int64]*level
	idx     map[string]*slot
}
```

这个教训在第 9 节复盘，先记住一句话：**画状态图比写代码快**。

### 3.4 每档 FIFO 和 O(1) 撤单

`Add` 的逻辑一句话：查档位表，没有就建档并插跳表，订单 `PushBack` 到队尾，同时登记索引。`Cancel` 则靠索引 O(1) 定位（`book.go`）：

```go
func (b *OrderBook) Cancel(id string) {
	s, ok := b.idx[id]
	if !ok {
		return
	}
	delete(b.idx, id)
	lvls := b.levelMap(s.side)
	lv := lvls[s.price]
	lv.orders.Remove(s.elem)
	if lv.orders.Len() == 0 {
		delete(lvls, s.price)
		b.priceSet(s.side).Delete(s.price)
	}
}
```

撤单必须 O(1) 不是洁癖：撤单发生在撮合循环之外，是高频操作，任何“扫一遍队列找订单”的实现，在单档堆了几万单时会直接拖垮引擎。

## 4. 撮合循环

### 4.1 成交价归谁

入口是 `Handle`：`'A'` 新增并立即尝试撮合，`'X'` 撤单。新增的这方叫**主动单**，盘口里等着的叫**被动单**。撮合循环全文（`engine.go`）：

```go
// match 撮合循环：最优买价 ≥ 最优卖价即可成交，直至无法撮合。
//
// active 是本次触发撮合的主动方向；成交价取被动方（先挂单方）价格：
//   - 主动买单吃卖盘 → 成交价 = 卖盘价（ask）
//   - 主动卖单吃买盘 → 成交价 = 买盘价（bid）
//
// 部分成交：撮合数量 = min(双方剩余量)，未成交完的订单留在队首继续参与下一轮。
func (e *Engine) match(active order.Side) {
	for {
		bid, okB := e.book.BestBid()
		ask, okA := e.book.BestAsk()
		if !okB || !okA || bid < ask {
			return
		}
		b := e.book.FrontBid()
		a := e.book.FrontAsk()

		qty := b.Qty
		if a.Qty < qty {
			qty = a.Qty
		}
		price := ask
		if active == order.Sell {
			price = bid
		}

		e.tradeNo++
		e.done = append(e.done, order.Trade{
			ID: fmt.Sprintf("T%d", e.tradeNo), BuyID: b.ID, SellID: a.ID,
			Qty: qty, Price: price, Seq: e.seq,
		})
		fmt.Fprintf(e.out, "TRADE %s %d@%d %s\n", b.ID, qty, price, a.ID)

		b.Qty -= qty
		a.Qty -= qty
		if b.Qty == 0 {
			e.book.PopBid()
		}
		if a.Qty == 0 {
			e.book.PopAsk()
		}
	}
}
```

循环里最容易被忽略的是成交价那两行：

```go
price := ask
if active == order.Sell {
	price = bid
}
```

主动买吃卖盘，成交价是卖价；主动卖吃买盘，成交价是买价。**成交价永远归被动方**——被动单挂出去的价格就是“我承诺的成交价”，主动单只能接受或离开。把成交价写成主动方价格是撮合引擎最常见的错误，尤其主动单连吃多档时，逐档价格必须逐档不同。

`seq` 是每笔订单到达引擎的顺序号，写进成交记录。FIFO 队列已经保序了，`Seq` 是留给审计和未来并发改造的“逻辑时钟”——队列位置可以变，顺序号不能变。

### 4.2 部分成交：剩下的单子不挪窝

撮合数量 `qty = min(双方剩余量)`，两边同时减。减完剩余的一方**不挪位置**：主动单没吃完就留在队首；被动单没吃完就留在自己档位队首，继续等下一个主动单。**FIFO 的队首不是“轮到谁”，而是“谁最早还没被吃完”**。`PopBid`/`PopAsk` 只在订单全部成交时才弹，弹完如果该档空了，顺手清掉档位表和索引。

### 4.3 一笔大单能穿多少档

`match` 是 `for` 循环而不是单次匹配：主动单量大时，会连续吃穿多个价格档位，每轮重新取最优价，直到 `bid < ask` 无法撮合。每轮成交是常数次 O(log n) 的档位操作（取最值 O(1)，弹档可能触发跳表删除 O(log n)），所以**一笔大单的撮合成本 = O(成交笔数 × log n)**——这就是拆档位数据结构的意义：让“吃穿盘口”这种极端情形也保持可预期。

## 5. 把 IO 挡在撮合循环外

`feed` 包把“读文件 + 解析”放进独立 goroutine，用无缓冲 channel 把事件逐条投给引擎（`feed/reader.go`）：

```go
func ReadFile(path string) (<-chan order.Event, <-chan error) {
	events := make(chan order.Event)
	errs := make(chan error, 1)
	go func() {
		defer close(events)
		f, err := os.Open(path)
		if err != nil {
			errs <- err
			return
		}
		defer f.Close()

		sc := bufio.NewScanner(f)
		for sc.Scan() {
			line := strings.TrimSpace(sc.Text())
			if line == "" {
				continue
			}
			ev, err := ParseLine(line)
			if err != nil {
				errs <- err
				return
			}
			events <- ev
		}
		if err := sc.Err(); err != nil {
			errs <- err
		}
	}()
	return events, errs
}
```

两个设计点：

1. **无缓冲 channel 自带背压**：读取 goroutine 每次发送都会阻塞到引擎消费完，读得快不会撑爆内存，事件顺序即文件行序。
2. **errs 缓冲为 1**：任何一步出错，写一条错误就 return，`defer close(events)` 保证调用方 range 能正常退出，主流程不会被卡死。

边界要说清楚：**这个并发只解耦了 IO，撮合本身仍是单 goroutine 串行**。撮合天然不适合多线程并行（状态有严格顺序依赖），业界做法是把 IO、解析、风控、撮合拆成不同阶段用队列连起来，撮合段保持单线程。

## 6. 测试与验证

撮合语义不靠人肉验证。10 个单测全绿，覆盖了最容易错的行：

| 测试 | 验证什么 |
|---|---|
| `book.SkiplistInsertMinMax` / `SkiplistDelete` | 跳表插入去重、Min/Max 正确、删除后层级收缩 |
| `book.OrderBookAddCancel` | 新增/撤单/索引一致性，档位删空清理 |
| `book.OrderBookPopCleansLevel` | 全部成交后档位、索引、跳表三者同步清理 |
| `engine.TestSampleInputFromProblem` | 示例输入 → 2 笔成交 + 最终盘口完全一致 |
| `engine.TestAggressiveBuyEatsAsk` | 主动买吃卖盘，成交价 = 卖价 |
| `engine.TestAggressiveSellEatsBid` | 主动卖吃买盘，成交价 = 买价 |
| `engine.TestCancelThenReAddGoesToBack` | 撤单后重新挂单，进入队尾（时间优先） |
| `engine.TestTimePrioritySamePrice` | 同价两单，先到先成交 |
| `engine.TestReadFileFlow` | feed 并发读取路径与逐行解析路径结果一致 |

测试数据（`testdata/sample.txt`，12 行 A/X 消息）：

```text
A,100000,S,1,1075    A,100001,B,9,1000
A,100002,B,30,975    A,100003,S,10,1050
A,100004,B,10,950    A,100005,S,2,1025
A,100006,B,1,1000    X,100004,B,10,950
A,100007,S,5,1025    A,100008,B,3,1050
X,100008,B,3,1050    X,100005,S,2,1025
```

这 12 行里藏着三个最容易写错的语义：

1. **第 8 行撤 100004**：挂 950 买价，从未成交过——撤未成交单，盘口里直接消失。
2. **第 10 行 100008 挂买 3 股 @1050**：它一来就触发撮合，因为最优卖价 1025 ≤ 限价 1050。**注意成交价是 1025 而不是 1050**——被动方价格。它先吃穿 1025 档队首 100005（卖 2），成交 `TRADE 100008 2@1025 100005`；剩 1 股继续撞同一档 100007（卖 5），成交 `TRADE 100008 1@1025 100007`，100007 剩 4 留在队首。
3. **第 11、12 行撤 100008 和 100005**：两笔都已成交出局，撤单被正确忽略——撤已成交单，直接返回不做任何事。

最终盘口：

```text
=================
ASK
1025: [4]
1050: [10]
1075: [1]
------------
BID
1000: [9 1]
975: [30]
=================
```

`1025: [4]` 就是 100007 剩的 4 股，印证“部分成交后剩余留在队首”。盘口数据来自 `LevelSummary`（`book.go`）：

```go
// LevelSummary 返回指定方向某价格档位的数量序列（按到达顺序）。
func (b *OrderBook) LevelSummary(side order.Side, price int64) []int64 {
	lv, ok := b.levelMap(side)[price]
	if !ok {
		return nil
	}
	out := make([]int64, 0, lv.orders.Len())
	for e := lv.orders.Front(); e != nil; e = e.Next() {
		out = append(out, e.Value.(*order.Order).Qty)
	}
	return out
}
```

测试断言用 `strings.Contains` 匹配 `1025: [4]` 这样的完整字符串，而不是单字段——撮合语义、盘口清理、输出格式任何一个环节出错，断言都会红。

## 7. 压测：本机可复现的基准

压测用 Go 标准 `testing.B`，三个方向：档位增删、新增+撤单、撮合全流程。数据在本机 WSL 环境复现，**不构成任何生产环境的性能承诺**——单机基准只能回答成本量级。

| 基准 | 规模 | 耗时 | 内存分配 | 折算吞吐 |
|---|---|---|---|---|
| SkiplistInsert | 10k 个不同价格档位 | 1.23 ms | 489 KB / 20,005 allocs | ≈ 8.1M 档位/秒 |
| SkiplistDelete | 10k 档位插入 + 10k 删除 | 1.47 ms | 489 KB / 20,005 allocs | — |
| OrderBookAddCancel | 10k 单新增 + 10k 撤单 | 3.39 ms | 2.28 MB / 50,505 allocs | ≈ 5.9M 单/秒 |
| EngineMatch | 100k 交替订单 → 50k 笔成交 | 66.8 ms | 51.1 MB / 1,149,614 allocs | ≈ 150 万单/秒 |

环境：WSL2（内核 6.6.87.2），go 1.22.2 linux/amd64，Intel Core i7-14700（28 逻辑核），15 GiB 内存。

数据里最值得看的不是吞吐，而是 **EngineMatch 的分配**：100k 单产生 1.15M 次分配，平均每单 11.5 次——订单对象、`list.Element`、`fmt.Sprintf` 的 ID 字符串、Trade 记录各占一部分。吞吐 150 万单/秒在单线程语义下够用，但这个分配画像直接说明第 8 节“内存池”为什么排在扩展第一位：**撮合逻辑本身不慢，慢的是对象生产与 GC 压力**。

## 8. 边界与扩展

| 未实现 | 需要的场景 | 为什么现在不做 |
|---|---|---|
| 涨跌停 / 熔断 | 实盘 A 股等带价格限制的品种 | 与撮合语义正交，属于前置校验层 |
| 手数约束（最小交易单位） | 股票按手、期货按合约乘数 | 数据模型加一列即可，不改变结构 |
| 多档一次性扫单的快路径 | 大单频繁吃穿多档时 | 当前 O(成交笔数 × log n) 已够；优化点在档位删除路径 |
| 无锁 / 细粒度锁并发 | 单线程撮合成为瓶颈（每核每秒百万级订单以上） | 撮合状态强顺序依赖，先优化单线程，再考虑分档加锁 |
| 内存池复用 Order 对象 | 订单峰值内存分配成为 GC 压力 | Go 的分配器在中等量级下足够；量级上来后优先考虑 pool |

边界结论：**当前实现是“语义完整、单线程正确”的基线版，生产化要加的是前置校验、快路径和无锁化，而不是改撮合语义本身。**

## 9. 复盘：如果再来一次

1. **买卖盘共档位的 bug，本可以画一张状态图避免**。写代码前只画了“数据结构选型”，没画“撮合时数据怎么流动”。如果先画：买单进队列 → 撮合时 `FrontBid` 和 `FrontAsk` 指向的队列关系——立刻会发现两侧读的是同一批队列。**先画状态图再写撮合循环，成本五分钟，省下两小时排错。**
2. **选型应该先写测试再动手**。Skiplist 的 `Insert` 去重语义、`Max` 的走法，都是写测试时才发现定义不清晰的。反过来，把测试当作语义说明书先写，代码是顺着测试长出来的，就不会有“实现写完了测试不知道断言什么”的尴尬。
